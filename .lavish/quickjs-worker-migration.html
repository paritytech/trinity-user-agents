Proposal · product workers · 2026-11-01

Move product workers from hidden web views to sandboxed QuickJS

Product workers run today in a hidden WKWebView (iOS) or WebView (Android). The OS kills those web views in the background, each costs about 15 MB, and they cannot run inside a Notification Service Extension. This page proposes an engine that runs workers inside the Rust core, keeps an escaped script away from key material, and is the same on iOS, Android, the NSE and the CLI.

Decision in five lines

  • Engine: QuickJS-NG through rquickjs, compiled to WebAssembly and executed by wasmi (pure-Rust interpreter, originally a Parity project) inside the core. Not native rquickjs in-process.
  • Why wasm: a QuickJS memory bug can only corrupt the worker's own linear memory. The core's keys, the SQLite DB and the keychain handles are outside anything the script can address. This holds in the main app and in the NSE, which shares the main app's keychain group.
  • Transport: the worker exchanges SCALE frames with ProductRuntime directly through a FrameSink. No loopback WebSocket, no relisten_ws_bridge.
  • Ownership: the core starts and stops the worker from its existing reference ledger. Hosts stop owning a JS engine and only supply the archive and HTTP.
  • Gate: phase 0 measures wasm-QuickJS on real devices. If the interpreter cost is too high for real workers, the fallbacks are listed in Options.

How workers run today

The core owns a per-product reference count. When it crosses zero it asks the host to start or stop the worker, and the host boots a hidden web view that talks back over a loopback WebSocket.

~15 MBper WKWebView after a run, ~7.9 MB idle (iPhone 17e, playground)
~0.3 MBper native QuickJS sandbox; 500 start in 40 ms (simulator)

Today's isolation is actually good. A WebKit exploit lands in the sandboxed WebContent process, which holds no keys. Moving the worker into the app process with plain native QuickJS would make security worse than today. This is the main reason the proposal puts QuickJS inside a wasm sandbox.
The NSE shares the main app's keychain. NotificationServiceExtension.entitlements lists $(AppIdentifierPrefix)$(APP_MAIN_BUNDLE), and the app's BUNDLE = $(APP_MAIN_BUNDLE) (polkadot-app/Configs/*.xcconfig). Being a separate process is therefore not a boundary on its own: native QuickJS escaped inside the NSE can read the same keychain items as the app.

Where the script runs: options

Which execution boundary product workers get. Each card shows what a QuickJS memory-corruption bug can reach. C was chosen.

A. Native rquickjs in the app process

escape reaches keys

The rquickjs-playground model: AsyncRuntime on a thread, LLRT globals, heap/stack/interrupt limits.

Gains

  • Fastest, smallest
  • Proven by the playground on both OSes

Costs

  • Weaker than today's WebContent sandbox
  • Heap limit ignores Rust-side allocations; long native calls are not preempted
  • Runtime is !Send: a thread per worker

B. Native rquickjs in a separate OS process

Android only

Android android:isolatedProcess="true" service; iOS has no equivalent beyond extensions.

Gains

  • Real OS boundary on Android (separate UID, no app data)
  • Native speed

Costs

  • iOS cannot spawn processes; the NSE shares the keychain
  • Two different designs to maintain
  • IPC hop per frame
chosen

C. QuickJS compiled to wasm, run by wasmi in the core

escape stays in linear memory

Guest: rquickjs + worker globals built for wasm32-wasip1. Host: wasmi with a small import ABI, inside truapi.

Gains

  • Same artifact on iOS, Android, NSE, CLI, browser
  • Memory cap covers all of QuickJS, fuel metering preempts everything
  • Store is Send: workers are tasks on the core executor
  • Host side stays safe Rust (unsafe_code = "deny")

Costs

  • Interpreter on an interpreter: slower JS (to be measured, estimate 3 to 10×)
  • wasi-sdk C toolchain in CI for the guest
  • +1 to 2 MB binary (wasmi + guest module)

D. Keep web views, harden lifecycle

status quo

Keep-alive tricks, faster reboot, state through host storage.

Gains

  • No new engine, full web platform
  • OS process sandbox

Costs

  • Does not fix background kills or memory
  • Impossible in the NSE
  • Two host-specific engines remain

Also rejected: JavaScriptCore JSContext without a web view (in-process like A, iOS only, no JIT outside WebContent anyway).

Why C was chosen over A + B

A combined A+B design gives Android a strong boundary and leaves iOS (main app and NSE) with none. C gives every platform the same memory boundary with one code path. If phase 0 shows wasmi is too slow, the cheapest improvement keeps C's design and swaps the wasm engine per platform: wasmtime with Cranelift on Android (JIT is allowed there) and wasmi or wasmtime Pulley on iOS, where JIT is forbidden. The guest module and import ABI do not change.

Target architecture

The worker becomes a core-owned task. The host provides two things the core cannot: the worker's files (dotNS/IPFS archive, already fetched by the host) and platform HTTP.

New crates

  • truapi-worker-guest: rquickjs + worker prelude, built to wasm32-wasip1, output embedded as bytes. Not a workspace member for host targets.
  • truapi-worker: wasmi embedding, import ABI, event loop, limits. Linked by truapi behind a native feature.

Event loop

One tokio task per worker drives the instance: deliver frame, fire timer, then call the guest's run_jobs until the job queue is empty or fuel runs out. Idle workers cost no thread. A whole worker is Send, so many workers share the core's existing executor.

Startup

Instantiate a pre-validated module (compiled once per process), then evaluate the prelude and entry module. A bytecode cache keyed by (contentId, engine version) skips parsing on later starts. Loading cached bytecode is acceptable here because it only ever runs inside the sandbox.

Security model

Attacker: a malicious product worker, or a benign one that triggers a QuickJS memory bug. QuickJS has a long fuzzing CVE history (UAFs, stack exhaustion). It has no JIT, which helps, but a C interpreter must be assumed exploitable.

LayerWhat it stopsMechanism
1 · globalsScript calling APIs it should notOnly prelude globals exist. No WebAssembly, SharedArrayBuffer, eval of bytecode, require, file system, Worker.
2 · linear memoryQuickJS bug reading or writing host memoryEvery guest load or store is bounds-checked by wasmi against the instance's own memory. Keys and DB live in host memory, which has no guest address.
3 · import ABICompromised guest abusing the hostAbout ten typed imports; every pointer and length validated; frames size-capped; fuzzed with arbitrary guest inputs.
4 · dispatcherProtocol-level abuseUnchanged: Dispatcher::for_execution(Worker), sessions, permission prompts, scanner tap rule.
5 · resourcesBusy loops, memory bombs, DoS of the NSEwasmi fuel per turn, linear memory max, wall-clock budget, frame rate limit. All enforced outside the guest, so long QuickJS builtins (regex, sort, JSON) are preempted too.
6 · side channelsTiming attacks on host secretsnow_ms coarsened, no shared memory, no threads in the guest.
7 · OS (optional)wasmi bugAndroid: run the worker host in an isolatedProcess later if threat model requires it. iOS: none available.

Residual risk

  • A bug in wasmi itself. Safe Rust, fuzzed, used in production by Substrate contracts. Much smaller surface than QuickJS.
  • A bug in our import handlers. Kept small and fuzzed as its own target.
  • Logical abuse through allowed protocol calls. Same as today.

Hard rules

  • Never load bytecode the product supplied; only source, or bytecode this engine produced.
  • No key-bearing operation is reachable through imports; signing stays behind TrUAPI methods and their consent flows.
  • Guest module hash compiled into the core, same pattern as truapi-verifiable.
  • Pin rquickjs and any LLRT pieces by version; vendor LLRT code we reuse rather than tracking main.

The worker environment

A worker stops being a hidden page. It gets a small, documented set of globals instead of a window with a DOM. This is a contract change products can observe and needs an amendment to the Product Manifest RFC.

Migration plan

Each phase ships on its own and leaves the web view path working until phase 5.

Spike and measure

scratch cratedecision gate

Build the guest (rquickjs on wasm32-wasip1) and a minimal wasmi host. Run playground/worker and js/scripts/pocket-battery.ts on a physical iPhone and a mid-range Android phone. Compare four engines: hidden web view, native rquickjs, wasm on wasmi, wasm on wasmtime (Cranelift on Android, Pulley on iOS).

Measure: cold start, idle and peak memory, time to first frame, frames per second through the client, and an NSE run under its memory ceiling.

Gate: wasmi stays the default if cold start is under 50 ms and a pocket render round trip is within 2× of the web view. Otherwise move to per-platform wasm engines, not to option A.

Core-owned worker, hosts behind a flag

iOS + AndroidUniFFI change
  • The ledger in host_logic/worker.rs starts and stops the QuickJS worker itself. request_worker_transition is only called for web view workers.
  • New HostBridge callbacks: resolve_worker_archive(product_id) (reuses the host's dotNS resolver and local storage) and http_request (URLSession / OkHttp). The core runs the Remote-permission check before calling it, so Android no longer needs its nativeHttp interceptor for workers.

  • Telemetry: worker restarts per hour, memory, start latency, compared by engine.

Default on, remove web view workers

removal

Delete the web view worker path on both hosts (TrUAPIWorkerBuilder, TrUAPIWorkerSupervisor engine code, worker use of the WS bridge), and the legacy host-api worker path behind isTrUAPIRuntimeEnabled if that has also been retired.

6

Workers in the NSE and in background tasks

RFC amendmentiOS NSE, Android FCM
  • Amend the Worker Lifecycle RFC: a push addressed to a product, or a BGTask window, is a new reference holder. It says today that scheduled wakeups are out of scope.
  • Link a slim core into the NSE. It does not today, and the core DB lives in Application Support, outside the app group.
  • Render-only profile: the worker receives the push payload and returns notification content. It can read its local_storage and nothing else: no signing, payments, SSO, chain access or statement store, no network. One worker at a time, tight fuel, 8 MiB heap under the NSE's memory ceiling.
  • The worker's local_storage must be readable from the NSE: either a read-only snapshot in the app group container, or the core DB moved there. Decide in this phase.
