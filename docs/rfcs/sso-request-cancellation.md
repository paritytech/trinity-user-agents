# RFC: SSO request cancellation

## Summary

The SSO channel gains a `Cancel` control message that names a request the pairing host's caller has withdrawn. The
paired host acts on it while serving other requests: a queued request is dropped before it prompts, and a running one
stops at its prompt or before its next allocation step.

## Motivation

[Request cancellation][cancel] stops a withdrawn call at the pairing host, but a request already published keeps running
on the paired host. Signing leaves a stale prompt on the phone. Resource allocation spends on the phone for a product
that has stopped waiting. A message alone cannot reach the prompt, because a paired host serves one request at a time
and reads the next message only after the current one is answered.

## Requirements

- **Reach**: a withdrawal reaches a request the paired host has queued or is prompting for.
- **Finality**: a withdrawn request never prompts after the withdrawal is read, and redelivery does not revive it.
- **Additive**: a paired host without the message serves every request as it does today.

## Approach

- **The message.** `Cancel` is appended to `v1::RemoteMessage` at the next explicit index, beside `Disconnected`, and
  names the withdrawn request's `message_id`. It means something only from the pairing host, since a paired host reads
  only its peer's statements.
- **When it is sent.** The pairing host sends `Cancel` when its caller withdraws a request; a host timeout sends
  nothing, so the phone may still finish. It goes alone in a request statement with its own id, on the session's
  request channel, and nothing waits for it. The store keeps one statement per channel and the later build wins, so the
  `Cancel` replaces its target: a phone that has not read the request never sees it, and one that has sees the
  withdrawal. It is sent only while its target is the newest statement built on the channel, checked and built under
  one lock; otherwise it would replace another request, and nothing is sent.
- **Reading it in time.** The Rust responder reads statements while it serves a request and applies a `Cancel` at
  once. Requests are still served one at a time, reading pauses once 64 are queued (a page already read is queued
  whole), and `Disconnected` keeps its place in the queue. A native wallet passes `Cancel` to `handle_sso_request`,
  which returns at once, and must do so as the message arrives rather than behind the request it withdraws.
- **What it stops.** A running request has its token fired and posts no response. A request not yet started never
  runs, and the responder's replay ledger records it as handled so redelivery does not revive it. A `Cancel` for a
  request not yet seen is remembered, up to 64 of them; one pushed out by a newer one is logged, and its request is
  served in full. Resource allocation checks the token before each resource and
  never abandons a step already under way.
- **Withdrawing the prompt.** The core drops the `confirm_user_action` future, and the host should dismiss its prompt.
  The bindings generated by `uniffi_bindgen` 0.32.0 cancel the Swift `Task` or Kotlin coroutine behind a dropped
  callback future; a version bump must re-check that. The wasm bridge passes no `AbortSignal`, so a browser host keeps
  its prompt until it is answered, and that answer authorizes nothing.
- **Peers without it.** The Rust responder, iOS and Android were each checked: an undecodable `Cancel` is logged, the
  session continues, and the target is served as before. Sent alone, it costs no other message.

## Trade-offs

- A cancel is fire-and-forget, and pairing negotiates no capabilities. `Cancelled` tells a product it stopped waiting,
  not that nothing happened: a resource allocated before the phone read the withdrawal stays allocated. [#478][478] is
  what lets a caller know the phone understood.
- A withdrawal after approval stops only the allocation steps not yet started.
- A withdrawn request with a newer one behind it keeps prompting on the phone.
- Waiting for the paired host's final answer was dropped: it makes an abort as slow as the prompt it aborts.
- A second channel for control messages was dropped. The per-account statement cap could still evict a request, and no
  host has used a second channel before.

## Open questions

1. iOS queues every SSO message behind the one it is serving, so a `Cancel` reaches `handle_sso_request` only after its
   target has finished. Its dispatcher needs to pass `Cancel` through at once.
2. Android decodes SSO in Kotlin and does not use the core's responder. It needs its own `Cancel` handling and prompt
   dismissal.
